# Windows MSVC 2022 build path — verification record

Written after actually running the documented MSVC recipe end to end on a clean
Windows box. Every claim below was observed, not inferred; the command output is
in the repository-free log directory named at the bottom.

The build and boot claims were taken into this repository's docs on 2026-11-01
(§ 2 records where). The one source-level blocker was worked around from outside
the tree (a `/FI` shim) purely to see how far the build and the title would get;
the fix it needs is [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md), "MSVC: the input layer
calls POSIX `clock_gettime`".

  >
  > - **Symptom:** `xboxrecomp/src/input/keyboard.c(189,27): error C2065:
  >   'CLOCK_MONOTONIC': identifier undeclared`, twice, and the whole build
  >   stops. MSVC has neither `clock_gettime` nor `CLOCK_MONOTONIC`.

  >   outside the tree (`cl /FI shim.h`) that maps `clock_gettime` onto

  >   title boots.
  > - **Where the fix belongs:** the `xboxrecomp` toolkit
  >   (`src/input/keyboard.c`), not this repository. Guard the hook with
  >   `#ifndef _WIN32`, or switch it to the toolkit's existing host-time
  >   abstraction in `src/platform/host_time.h`.

## 3. The one source blocker, precisely

```
C:\otogi1\xboxrecomp\src\input\keyboard.c(189,27): error C2065: 'CLOCK_MONOTONIC': identificador não declarado
C:\otogi1\xboxrecomp\src\input\keyboard.c(190,23): error C2065: 'CLOCK_MONOTONIC': identificador não declarado
```

Context (`xbox_InputKeyboardState`, the `RECOMP_AUTOPAD` hook):

```c
if (getenv("RECOMP_AUTOPAD") != NULL) {
    static struct timespec t0;
    struct timespec now;
    if (t0.tv_sec == 0 && t0.tv_nsec == 0)
        clock_gettime(CLOCK_MONOTONIC, &t0);
    clock_gettime(CLOCK_MONOTONIC, &now);
```

MSVC defines `struct timespec` but has no `clock_gettime()` and no
`CLOCK_MONOTONIC`; the compiler emits `warning C4013` ("assuming extern
returning int") and then fails on the undeclared constant. The same file calls
`getenv`, hence three `C4996` deprecation warnings alongside.

**Scope of the blocker.** `xbox_input` is where MSBuild stops, and every other
`clock_gettime` site in the toolkit was checked to confirm it is the only one
MSVC actually compiles:

| Site | Why it is not an MSVC blocker |
|---|---|
| `src/input/xinput_device.c:318` | inside the `#else /* !_WIN32 */` arm that starts at line 217 |
| `src/platform/win32_compat.c` (6 sites) | on `WIN32`, `platform` is an **INTERFACE** target (`src/platform/CMakeLists.txt:39-43`), so this file is never compiled by MSVC at all |
| `src/apu/apu_sdl2.c`, `src/video/fb_present_sdl.c` | SDL2 path, not built on Windows |
| `src/apu/apu_wav.c:45`, `src/platform/host_time.c:49` | both are inside `#else` POSIX arms of a `_WIN32` split (`apu_wav.c:10/30`, `host_time.c:12/34`) |

So: one file, two lines. Everything else in the Windows build compiles.

## 5. Prerequisites the docs do not mention

1. **A Visual Studio install does not imply the C++ workload.** The machine had
   VS 2022 Community with MSBuild and `common7/`, but no `VC/` directory at all:
   no `cl.exe`, no toolset. Check with:

   ```powershell
   & "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\vswhere.exe" `
       -latest -products * -require Microsoft.VisualStudio.Component.VC.Tools.x86.x64 `
       -property installationPath
   ```

   Empty output = workload missing. Adding it needs the *Desktop development
   with C++* workload for the IDE, or the standalone **Build Tools** with
   `Microsoft.VisualStudio.Workload.VCTools` (what was used here; no IDE).
2. **CMake is not installed by default.** `cmake` was not on `PATH` and the
   `C++ CMake tools for Windows` component was absent. The docs assume `cmake`
   exists. Say where it comes from (component, standalone installer, or `choco
   install cmake`).
3. **Disk space fails the install silently-ish.** With 4 GB free the workload
   installer aborts in its pre-check: `Pre-check verification failed with
   error(s): SizePreCheckEvaluator`, exit code `-2147024784` (`0x80070070`,
   `ERROR_DISK_FULL`), with no message on the console. Recommend ≥ 8 GB free, and
   name that exit code so the failure is recognisable.
4. **Installer CLI traps** (worth one sentence in the docs, because the CLI is
   the only sane path on a headless box):
   - `setup.exe modify` rejects `--wait` and `--log` (exit 87, installs nothing).
   - `--installPath` must be quoted through `Start-Process -ArgumentList`, or the
     path splits on its space and you get "cannot find an installed product
     matching … installPath: C:\Program".
   - `--path cache=<dir>` makes the installer fail with `0x80070005` if the
     directory is on a volume the elevated service cannot reach (a RAM disk, for
     example). Keep the cache on the system volume.

## 6. Build observations worth a line in the docs

- The MSVC build also builds the toolkit's smoke executables
  (`d3d8_smoke.exe`, `d3d8_states_smoke.exe`, `d3d8_gamma.exe`, `d3d8_a8.exe`).
  That is fine, but it is not mentioned anywhere and adds a few minutes.
- Warning volume on a clean build: 0 errors after the fix, ~100 warnings, almost
  all benign MSVC pedantry (`C4005` macro redefinition in `nv2a_regs.h`,
  `C4100` unused parameter, `C4996` `getenv`, `C4457` shadowing). Worth saying
  explicitly, so nobody treats the warning wall as a failure.
- `C4996` can be silenced wholesale with `_CRT_SECURE_NO_WARNINGS` in the
  Windows branch of `CMakeLists.txt`; that is a build-config choice, not
  required for correctness.
- `/bigobj` is already set for `otogi1`; that is why the 27 generated chunks
  compile. Keep it — removing it is the classic way to break this build.
